眼见为实。四张截图是本 session 在同一个 harness 里逐个点出来的（appshot 脚本，公开在 PR 里）。它顺带证明了两件事：(1) Octane 在 #459 合并后的 upstream main 上端到端可用 —— 首屏、事件、更新都通；(2) 四份实现的 UI 语义逐像素对齐（同 class 结构、同数据生成器），黑盒对比才成立。

三次独立进化，一张考卷

Lynx 把 UI 拆到两条线程上：主线程负责画，后台线程负责想。 任何框架落到这块土壤上，都要重新回答同一组问题 —— 谁渲染第一帧？更新怎么过线？两棵树怎么对上号？

三个互不抄袭的答案摆在一起，收敛处就是平台的共性， 分歧处就是设计的自由度。

方法论开宗明义。这不是"谁更快"的跑分帖：三个框架是三次独立实验。它们在哪里给出同样的答案（都要命名、都要编码、都要 hydration），说明那是平台强加的必修题；在哪里分道扬镳（渲染模型、传输编码、第一帧驱动方式），才是真正的设计选择。后面每一章都沿着这条线走。

一 · 编程模型

同一个组件，三种写法 —— 以及编译器各自把它变成了什么。

第一章：先看开发者手里的代码长什么样，再看编译产物 —— 编程模型的分歧从编译边界开始。三份源码都来自 benchmark 仓库里真实的 app（packages/benchmark/apps/），不是为 slides 编的。

同一个 Row，三种源码

ReactLynxApp.tsx · JSX + hooks
Row.tsx
const Row = memo(function Row({ row, isSelected,
    onSelect, onRemove }: RowProps) {
  return (
    <view className={isSelected
        ? 'row danger' : 'row'}>
      <text className="col-id">{row.id}</text>
      <text bindtap={() => onSelect(row.id)}>
        {row.label}

Vue LynxApp.vue · SFC + ref
App.vue
<template>
  <view v-for="row of rows" :key="row.id"
    :class="selected === row.id
      ? 'row danger' : 'row'">
    <text class="col-id">{{ row.id }}</text>
    <text @tap="select(row.id)">
      {{ row.label.value }}
    </text>
  </view>

OctaneApp.lynx.tsrx · 方言 + hooks
Row.tsrx
function Row(props: RowProps) @{
  <view class={['row',
      props.isSelected && 'danger']}>
    <text class="col-id">{String(props.row.id)}</text>
    <text bindtap={() => props.onSelect(
        props.row.id)}>
      {props.row.label}
    </text>
  </view>
}  // @{…}: 隐式 return 的组件体

表层几乎同一门语言：都是组件 + 属性 + 事件。Octane 用 React 的 API （useState / useCallback），但语法进了编译器方言 —— @{…} 组件体、 @for (… ; key …) 控制流。

三份都是真代码。ReactLynx 和 Octane 几乎逐字对应 —— Octane 刻意兼容 React API，hooks 从 'octane' 导入即可。差别在语法层：.tsrx 是 JSX 超集，@{ } 表示"语句体组件、最后的 JSX 隐式返回"，@for/@if/@switch 是一等控制流（不是表达式里的 map/三元）。这不是语法糖趣味题：控制流进了语法，编译器就能拿到 结构级 的静态信息 —— 这是它和 ReactLynx 编译路线最重要的共同点，也为第四章"Octane 拿到了 intrinsic 信息却没用在传输上"埋下伏笔。

Vue 侧：模板本来就是编译器方言，v-for/:key 与 @for 同构。Vue 的独特处是响应式在数据层（ref/shallowRef），不在组件重渲染层。

Octane：React 的 API，编译期的语义

React / ReactLynx运行时按调用顺序记账
rules of hooks
// hooks 靠调用顺序定位 →
// 不许写进 if / 早退

}

// 依赖数组手写，漏了自己背锅

compile-time slots

  useState(0)   // ✓ 合法
}

// 编译器从闭包捕获自动推导

同一个 API 表面，把"规则"从运行时纪律挪进编译器 —— 和 React Compiler 的方向一致，但走得更远：语义本身就是编译期的。

这是 Octane 最漂亮的编程模型创新。hooks 按"编译期调用点 Symbol"寻址而不是按运行时调用顺序，所以条件、早退里都能用；useEffect/useMemo 的依赖数组由编译器从闭包捕获推导（hook-deps.js，1363 行）。React 团队用 lint 规则 + React Compiler 逐步逼近的东西，Octane 直接建在了语义里。这一点对三个框架都成立着提醒：编译器能承担的正确性，不要留给运行时纪律。

对 Vue 的镜像：Vue 的 setup() 天然没有 hooks 顺序问题（响应式对象本来就是按引用的），所以这题 Vue 用另一种方式早就答了。

RL 和 Octane 都把静态结构折成常量、动态位留成"洞" —— 但 RL 的壳是 代码（create() 直接跑 PAPI），Octane 的壳是数据（plan 交给运行时解释、 更新仍走重建 + diff）。Vue 则把两条路各占一格：vdom 走 diff，vapor 走定点绑定。

术语：PAPI = Lynx 引擎的元素操作原语（__CreateView / __SetAttribute / __FlushElementTree…），双线程版的"DOM API"。

关键分野在"编译掉了什么"。三家都做静态提升（λ holes. tree 的部分求值），但残差的形态不同：RL Snapshot 的 create() 是编译到 code 级的残差（打进两个 bundle，MT 直接执行）；Octane 的 plan 是 data 级残差（结构常量在 bundle 里，但由运行时解释、且更新路径每次重建 Blueprint 树再 diff —— PR #343 的结论：compiled ≠ vdom-free）；Vue vdom 的 Block/patchFlags 是 addressing 信息、结构仍由运行时 ops 流式重放，vapor 则把结构做成 REGISTER_TREE 的 data 残差 + 每洞一个 effect。

完整框架都在后台线程；
分歧是主线程上放多少

ReactLynx
BG：完整 Preact + 应用 MT：一遍式渲染器（preact-render-to-string fork，无 effects 无调度）+ Snapshot create()
Vue Lynx
BG：完整 Vue + 应用 MT：ops 解释器；开 IFR 后 = 再放一个完整 Vue + 应用
Octane
BG：完整 universal 运行时 + 应用 MT：命令批接收器 + 一遍式渲染器（hooks 冻结成常量、effects 为 no-op）

三家都编译两份、装进一个 bundle。RL 和 Octane 给主线程的是阉割版： 只会画第一帧的一次性渲染器。Vue 的 IFR（instant first-frame：主线程先画首帧再交棒） 今天还把整个框架再搬一遍 —— 三者中最重的主线程配置。

Driver 轴的第一次亮相。ReactLynx 的 MT 切片跑的是 renderToOpcodes —— preact-render-to-string@6.0.3 的 fork，改成往 SnapshotInstance 树上写；无 diff、无 commit、无调度、options._skipEffects，setState 静默丢弃。Octane 的 main-renderer.ts 开头就自我声明"PrimJS-safe 一遍式渲染器 ABI"：useState 返回冻结值 + no-op setter，事件 prop 被剥掉换成 event marker。两家独立收敛到同一个答案：第一帧不需要框架，只需要框架的一次性投影。

Vue Lynx 的 IFR（mts-runtime driver）把完整运行时再放一遍，hello-world MT bundle 83→169KB —— #352 的 D2（vapor one-shot driver）正是要走向 RL/Octane 的答案。这一页给第四章"互相借鉴"备好了论据。

把三家响应式压进一页。ReactLynx：setState 走 Preact，组件重渲染 + BackgroundSnapshotInstance 记录变化为扁平补丁数组（CreateElement=0/InsertBefore=1/SetAttribute=3…），JSON 过线，MT snapshotPatchApply 查 id 跑编译好的槽位更新器。Vue：vdom 与 RL 同粒度（组件 diff），vapor 只跑被改的 effect —— 但两者产出同一种 numeric ops。Octane：hooks 槽位标脏 → 调度最近可重放的组件 owner（#578 之前是整个根！）→ 重跑编译组件产出 blueprint 树 → 与保留记录 diff → 版本化命令批。注意"头/尾"的解耦：头部（响应式）决定生成多少变更，尾部（传输+应用）决定每条变更的单价 —— 第三章的数字正是这两个因子的乘积。

二 · 坐标系

unified benchmark 的六列结构坐标 —— 把三个框架放进同一张地图。

第二章：vapor 分支建立的四轴模板矩阵（#321/#325，vue-lynx/internal/matrix）给了我们一套框架无关的语言。这一章不发明新词，只把 ReactLynx 和 Octane 放进已有的坐标系里 —— 位置本身就是结论。

一个 UI 子树 = λ 洞. 树

编译器对模板做部分求值：静态部分折叠成残差（骨架）， 动态部分留成参数（洞）。每家框架的"模板机制"， 只是给残差选了一种表示、给洞选了一种命名。

六列
Staging 残差什么形态：ops → data → code → native Naming 跨线程身份的单位：node / block Addressing 怎么找到节点 Provider 谁物化：BTS（后台线程）/ MTS（主线程脚本）/ Engine（引擎） Lifetime persistent / ephemeral Delivery 残差何时到主线程：runtime / bundle

一页背景，够用即可。这套坐标出自 GRAPH-ENG-REPORT §1：Staging 的 interp/compiled 分界就是 Futamura 分界（data=懒 AST + 通用解释器；code=每模板编译出的 create()，解释器被特化掉；native=引擎持有原型、逐节点 JS 都没了）。Naming 决定跨线程 wire 上的身份成本：每节点一个 id（node），还是每模板块一个基址 + 偏移（block）。这六列描述"残差怎么物化"；#352 又补了两列描述"谁来驱动第一帧、两棵树怎么交接"（Driver/Handover），本章末尾用到。

这张表是全章的地基。三个校准点：(1) RL Snapshot ≡ Vue 的 vdom +b（Code-Template）—— GRAPH-ENG-REPORT §1.4 的"hard conclusion 1"，坐标完全相同，谁也不比谁更 native；(2) Octane 的更新路径落在 ops/node —— 和 vue vdom 同格（下一页展开）；(3) Driver/Handover 两列上 Vue 是少数派：mts-runtime（整个框架再跑一遍）+ stream 等价比对（D1 已把 tree handover 做出来，默认还没切）。

Octane 的 repair 语义：adoption 失败时确定性地拆掉重画并上报 mismatch 事件 —— 比 Vue 旧 stream handover 的"整页回退"更细，但比 RL 的逐子树 patch 粗。

结构上同一格，性能差一个数量级（下一章的实测）—— 于是矩阵长出了两根新轴：WireEncoding 与 WireValidation。 差异全部住在传输层，不在架构里。

PR #343 的核心发现，一页讲完。结构六列上 Octane 就是 vdom +ifr：同是 vdom 渲染模型（重建树 + diff）、同是 ops 级 streaming、同是每节点命名随机寻址、同有 MT 第一帧。它们在 select@10k 上差 13×（#343；本 session 在 #578 后复测仍差 8.1×）。旧坐标系解释不了这个 gap —— 所以补两列：编码（一条扁平数字数组 vs 每命令一个对象过 structured clone）、验证（无 vs 每条消息两侧各验一遍）。这也是坐标系方法论的胜利：解释不了的差异，说明少了一根轴。

注意公平性：这里说的是"结构坐标同格"，不是"实现等价"—— Octane 的 commit→ack→complete 三段协议、per-changed-node 快照句柄等都折进这两根传输轴里读。

同一次点击，两种过线方式

Vue：一条扁平数组opcode + 操作数连排
internal/src/ops.ts
[ SET_CLASS, 1042, "row danger",
  SET_CLASS, 987,  "row" ]
// 一次 flush = 一条消息
// 解释器：switch 循环，无分配
// 验证：无（信任同源两端）
Octane：命令对象 + 全量验证structured clone 逐字段走
core/protocol.ts
{ protocol: 1, renderer: 'lynx',
  root: 'r0', version: 41, batch: [
    { kind: 'update', id: 1042,
      props: [['set','class','row danger']] },
    … ] }
// 每 commit 三段：commit → ack → complete
// 两侧都跑 validator（逐属性走查）

编码差的是常数，验证差的是随属性数线性增长的热路径成本 —— 而且每条消息、每次点击都在付。

把抽象的"传输轴"落到字节上。Vue 的 ops 是一条数字扁平数组（opcode+操作数），MT 端一个 switch 循环解释，整个 flush 一条消息过线。Octane 每个 commit 是一个嵌套命令对象树，走 ContextProxy 的 structured clone；协议还规定 commit→ack（带每个变更节点的公共句柄增量）→complete 三段往返；两侧 validator 逐字段检查 —— protocol.ts 的注释原话是"this protocol never falls back to postMessage"，工程上非常严谨，代价是每条消息都在为"防御性"付费。第四章会公道地说：这种显式契约 catch 到了真 bug（#459 正是 validator 报的），错的不是验证本身，是把它放在生产热路径上无差别地跑。

第一帧的两问：谁来画，怎么交接

Driver — 第一帧谁渲染Handover — 两棵树怎么对上
ReactLynx mts-oneshot：render-to-string fork，一遍走完 tree-adopt：hydrate(before, after) 树级 diff，分歧只赔子树
Octane mts-oneshot：冻结 hooks 的一次性渲染器 snapshot-adopt：逐节点比对认领，失败 → 确定性 repair
Vue Lynx mts-runtime：完整 Vue 再跑一遍（MT bundle 83→169KB） stream 等价比对 → D1 tree-adopt 已建成（中途分歧 −79%/−98% 原生调用）

两家独立收敛 = 平台在说话：第一帧要的不是框架，是框架的一次性投影； 交接要的不是逐条重放，是把已画好的树认领过来。

本章最重要的收敛证据。ReactLynx：renderMainThread 用 preact-render-to-string fork 一遍式产出 SnapshotInstance 树，然后 MT 把整树 JSON 发给 BG，BG hydrate 时把 MT 的 id 认领到自己的实例上（hydrationMap + updateId），分歧走 diffArrayLepus 局部补。Octane：main-renderer 冻结 hooks 一遍渲染，快照随 main-ready 回给 BG，BG 首次 commit 与快照逐节点比对，命中则跳过 create/insert 直接 re-own PAPI 节点，不命中确定性 repair + 上报 mismatch。两个团队没有互相看过代码（Octane 明确 no ReactLynx imports），却在这两根轴上给出同一答案。

Vue 的自省：我们的 IFR 是"把框架整个搬上 MT 再跑一遍"，handover 曾是 stream 等价比对（顺序敏感，弱于树比对）。#352 的 D1 已把 tree handover 建成并实测（中途结构分歧从整页重建降到局部修补），D2（one-shot driver）在路线图上。方向就是本表的右上角。

第四章：评判。原则：只点名有代码出处或实测支撑的条目；夸和批各给各家。

Octane 做对的事，比想象中多

✓ 平台细节的敬畏第一帧默认推迟到引擎 __RenderPage 之后 —— 因为 PageConfig（defaultOverflowVisible 等）在 MT 脚本求值后才就位，早画会被裁剪。多数团队会踩的坑，它绕开了
✓ 事件 token 带优先级__AddEvent 安装的 token 内嵌 priority，省掉每次点击一趟 MT 往返；传播路径上的多次触发合并成一个 event scope
✓ 真·list 回收componentAtIndex / enqueueComponent / componentAtIndexes 全套接入，LIS 最小化 update-list-info；12 行窗口只建 12 个物理 cell（0.012× eager）
✓ IFR + adoption一遍式 MT 渲染器 + BG 逐节点认领 + 确定性 repair —— 与 ReactLynx 独立同构；文档明确拒绝把"BG 渲染的预览"错标成 IFR
✓ 诚实的自审status.json 逐条区分"源码/测试/构建证据"与"原生证据"；divergence 全部成文

先夸，且都是硬夸。这些不是礼貌分：__RenderPage 时机（main-thread.ts:110-118 的长注释引用了 TemplateAssembler::DidVMExecute）说明作者真读了引擎；事件 token 带优先级（native-events.ts:73-83）是对"跨线程往返最贵"的正确直觉；list 回收深度接入是很多移植框架直接放弃的部分。结论先行：Octane 不是"不懂 Lynx 的 web 框架"——它在单点工程上常常最讲究，问题出在少数几个系统级预设上。下一页说那几个。

Octane 的四条弯路

✗ 传输当函数调用用每 commit 一个命令对象树过 structured clone，三段协议（commit→ack→complete）+ 双侧全量验证 —— 把 web 单 realm 的"消息不要钱"直觉带进了以 wire 为热路径的平台。点更新 10×+ 的直接来源
✗ 整树重放到 08-05#578 之前任何 setState 重渲染整个根（基线自述"hundreds of times slower"）；scoped updates 落地仅数日，portal / 活跃边界仍回退整根
✗ realm 假设#459：validator 用 realm-local 原型身份判"plain object"，web 双 realm 下拒掉所有消息 —— 同 realm 直觉的教科书案例
✗ 私有注入承载事件BG 事件靠 monkey-patch lynxCoreInject.tt.publishEvent —— 引擎私有面，一次升级就全体失聪；公开 string-event 契约还停在 blocked 里程碑

四条里三条是同一个病根：把线程边界当进程内边界。 编译器拿到了 intrinsic 的结构信息（plan + 槽），wire 上却一个字节都没用。

批评要说到病根。Octane 的编译器明明产出了与 Snapshot 同级的结构信息（plan 常量 + propsSlot 洞表），完全可以像 RL 那样把结构打进两个 bundle、wire 上只传 (模板 id, 槽值)。今天它的 wire 却是逐节点命令对象 —— 编译期的收获在传输层全部丢弃。这就是第二章坐标"Staging=ops / Naming=node"的由来：不是没有信息，是没用。加上验证常开与三段往返，形成"每条消息的固定税"。#578 修的是第二条（重放范围），不动这条传输税 —— 本章复测数字会印证这个预判。

ReactLynx：最完整的答案，和它的账单

✓ Snapshot = code 级残差静态壳编译成 create() 打进两个 bundle；wire 上只走 (snapshot id, 槽值) —— Staging/Naming/Delivery 三列的完全体
✓ 一遍式 MT driver第一帧用 render-to-string fork，不搬完整框架；MT bundle 只多编译产物不多运行时
✓ tree-adopt hydrationhydrate(before,after) 树级认领 + 分歧局部补 + 事件 id swap 重放 —— 决定论从正确性要求降级为性能优化
✗ fork 税pinned Preact fork + preact-render-to-string@6.0.3 fork，靠 mangled 私有名（__c、__s…）缝合 —— 永久维护税
✗ 双份世界的语义缝组件在 MT 以"无 effects、冻结 state"再跑一遍：'background only' 指令、useEffect shake、25 次 settle 循环……每条都是为语义缝打的补丁
✗ 首屏整树 JSONhydration 把整个首屏树 stringify→parse 跨线程 —— O(首屏) 的交互路径成本，专设了 timing 打点

RL 是这张地图上覆盖最全的实现——三列完全体 + oneshot + tree-adopt，第二章表里它一家全绿。但账单真实存在：fork 两个上游库并伸手进 mangled 内部（rl-insights 的"what not to copy"第一条）；双切片让每个组件活在两种语义下（MT 一次性 vs BG 持续），所有 'background only' / shake / settle 机制都是这条缝的胶带；首屏交接是整树 JSON。Vue 的 D1 学的是它的 handover 思想，但拒绝 fork —— 用 @vue/server-renderer 的 sink 或 vapor 编译产物本身。

Vue Lynx：wire 最干净，第一帧最重

✓ numeric-flat wireopcode+操作数一条扁平数组，switch 解释，无验证 —— 三家最便宜的传输；Octane 对照实测其价值 = 一个数量级
✓ BG 对 IFR 无感知IFR 全部在 MT 侧实现，BG 零协议面 —— RL 要 BG 配合 hydrate + swap 表，我们不用
✓ 11 格矩阵纪律每根轴一个决策点、每格一个 status、逐 flag 归因 —— 三家里唯一能做因子分解的实现
✗ mts-runtime driverIFR = 完整 Vue 再上 MT（83→169KB）；RL/Octane 都证明了一遍式投影就够 —— D2 是正确方向
✗ stream handover（已修）顺序敏感的逐帧比对，弱于 Vue 自家 DOM SSR 的树级 hydration；D1 已建成 tree-adopt，默认待切
✗ 残差 runtime 投递vapor 结构默认 REGISTER_TREE 过线（+b! / +b:c 已探明 bundle 投递路径，未成默认）

自省同样点名。Vue 的强项恰是 Octane 的弱项（wire），弱项恰是 RL/Octane 的强项（第一帧 driver）——三家互为镜像，这就是第五章"共性清单"的实证基础。11 格矩阵纪律值得单独说：它让"归因"成为可能——本 deck 能把 Octane 的差距拆到两根传输轴上，正因为 Vue 侧每根轴都有单变量 cell。

2 · 身份认领原语引擎级 adopt/remap API：把"一棵已画好的树"的元素身份批量转移给另一组 id（RL 的 refMap、Octane 的 adoption、Vue D1 的 matchTrees 三度重复发明）。块级命名（基址+偏移）让表 O(实例) 而非 O(节点)
3 · Element Templates 作为共享 staging 靶native 级残差（__CreateElementTemplate 族）是三家 code/data 残差的共同上界 —— 一次平台实现，三家的模板一起上 engine 档
4 · 公共事件契约Octane 靠 monkey-patch lynxCoreInject 收事件、RL 靠字符串握手 —— 把 string-token → BG 路由做成公开 API，附优先级语义（抄 Octane）

每条都从对比里长出来。1 是 Octane 弯路的反面 + Vue 实测的正面；2 是三度重复发明的直接合并（且 D1 实测：块命名让认领成本从 46ms 降到 2ms —— 平台若原生提供 remap，这 2ms 也能归零）；3 是矩阵早已指出的方向（native staging 对三家一视同仁，engine-NA-on-web 的探针已备好描述符）；4 有现成的反例（私有注入）和现成的正例（token 带优先级）。这一页可以直接改写成给 lynx-family 的 RFC 提纲。

六 · 老问题，
新问题

这些框架差异，哪些是 Web 吵了十年的旧账，哪些是 Lynx 双线程新开的账？

第六章：把坐标系的轴分成两堆 —— Web 也有的，和 Lynx 特有的。这决定了哪些结论可以从 Web 社区平移过来，哪些必须在 Lynx 上重新测。

八根轴，两种出身

Web 旧账
render model：vdom diff vs 细粒度 effect —— js-framework-benchmark 吵到今天的同一题 Staging 的存在性：模板编译/静态提升 web 也有（cloneNode 就是 native 档）
Lynx 新账
Naming —— 单 realm 里指针即身份，跨线程必须发明 id Delivery —— 残差"何时过线"在 web 无意义 WireEncoding / Validation —— web 没有热路径消息边界 Driver / Handover —— 第一帧双渲染与认领（web 仅 SSR 场景有其远亲）

八根轴里六根是 Lynx 双线程新开的账 —— 这就是"web 框架直接移植"注定踩坑的结构性原因：它们没有这六根轴的概念。

分类本身就是结论。web 单 realm：指针即身份（Naming 消失）、调用即送达（Delivery/Encoding/Validation 消失）、首帧只渲染一次（Driver/Handover 只在 SSR 时出现远亲）。Lynx 把 UI 劈成两个 realm，六根新轴同时张开。Octane 的三条弯路（clone 传输、常开验证、realm 假设）全部落在"新账"区 —— 不是工程能力问题，是概念清单里缺了这几项。反过来，Octane 的编译语义创新（hooks slot、依赖推导）落在"旧账"区，平移无损，好东西照样好。

VDOM vs Signal：Lynx 把两边的赌注都放大了

VDOM 在 Lynx 多赚的react / vdom / octane
batch 是天然形状
· 一次 commit = 一次 diff =
  一条消息 —— 批处理免费
· diff 产物天然是"最小 ops 集"，
  正好是 wire 想要的东西
· create/首帧：一遍式投影容易做
  （render-to-* 早有生态）
Signal 在 Lynx 多赚的vapor
不重渲染 = 不重发
· 点更新零 diff：selectStorm@30k
  vapor 429ms vs vdom 5367ms（12.5×）
· 但代价前置：必须先建 Naming
  （effect 要能"指名"远端节点）
· web 上 signals 省 diff；
  Lynx 上还省 wire —— 双重红利

Web 的结论不能白拿：Lynx 给 VDOM 发了"批量免费"的新牌， 也给 Signal 发了"wire 最小化"的新牌 —— 但 Signal 的牌必须先付 Naming 的门票。matrix 的 vapor 诸格，就是这张门票的精算表。

本页回答"VDOM/Signal 对 Lynx 的友好度"。友好度不是一维的：(1) 更新路径 signal 完胜且被 wire 放大（不重渲染 ⇒ 不重编码 ⇒ 不重解释）；(2) 批量/创建路径 vdom 并不吃亏 —— octane updateStorm 反超、react create 领先都是证据；(3) signal 的隐藏成本在 Lynx 被显式化：web 上 effect 拿着 DOM 指针就能写，Lynx 上必须有跨线程命名 + 寻址机制（vapor 的整个 +b 工程），这在 web 是不存在的工程量。所以"谁更友好"的诚实答案：交互重的 UI，signal 的双重红利值回门票；静态重的 UI，vdom+模板（RL Snapshot / vdom+b）已经贴着地板。

IFR 是 SSR 的韵脚，不是它的复刻

Web SSR + hydrationLynx IFR + handover
第一帧生产者服务器（跨机器）主线程（跨 realm，同设备）
一遍式渲染器renderToString 生态成熟RL fork 之 / Octane 自建 / Vue 待 D2
认领机制DOM 树遍历 + 就地绑定id 认领表（refMap / adoption / D1）
分歧代价hydration mismatch → 局部重渲染同构：局部补（RL/D1）或 repair（Octane）
独有难点序列化数据、流式事件重放（画得出但听不见的窗口）、id realm 对齐、每台设备都在跑

RL 的 opcodes 干脆就是同一个渲染器的 SSR 输出档 —— 但 Lynx 的新难点是真的： 第一帧和框架同机不同 realm，事件会在交接窗口里到达。

给 Web 背景的读者一座桥。Driver/Handover 轴在 web 的远亲是 SSR/hydration：一遍式渲染器（renderToString）、认领（hydrate）、分歧策略（mismatch 重渲染）——概念全对得上，RL 甚至用同一份 fork 同时供 IFR 和 SSR（__ENABLE_SSR__ 下 opcode 是第二输出）。但三个 Lynx 独有难点让"直接搬 SSR 方案"不够：(1) 交接窗口的事件缓冲与重放（RL 的 delayEvents + idSwap、Octane 的 FIFO replay，web 的 hydration 常直接丢）；(2) id 在两个 realm 各自计数，必须显式对齐/认领；(3) SSR 每次部署跑一次，IFR 每台设备每次冷启都跑 —— 一遍式渲染器的每毫秒都乘以 DAU。

五问，五答

1 · 模型与位置三家都是"编译期折残差 + 双切片"；RL = code/block/bundle 完全体，Octane 更新路径落在 ops/node（= vue vdom+ifr 同格），Vue 铺满 11 格做归因
2 · 性能后果结构同格下，传输两轴独立造成点更新数量级差距；批量摊薄后 Octane 渲染器并不慢；#578 后整树重放已修，传输税仍在（本次实测）
3 · 好设计 / 弯路抄 Octane：hooks 编译语义、事件优先级 token、__RenderPage 时机。抄 RL：一遍式 driver、树认领。抄 Vue：flat wire、BG 无感 IFR。弯路各一页，全有出处
4 · 共性 → 平台七件套三度重复发明；四条 Lynx for Framework API 建议（标准 ops、认领原语、ET 共享靶、公共事件契约）
5 · 旧账 / 新账render model 是 web 旧账可平移；六根新轴是双线程新账 —— signal 在 Lynx 有双重红利但要付 Naming 门票，vdom 拿到批量免费

总结页。每一格都能跳回对应章节的证据 slide。如果只记一句话：三个框架的分歧集中在平台没提供的地方 —— 平台提供了的地方（list 回收），三家一致。
