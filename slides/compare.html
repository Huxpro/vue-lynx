Octane 没有"慢的渲染器"—— 它有一组在单线程环境里免费、在跨线程环境里按 N 计费的 默认假设。web 上这些账单是零，所以从没有人看过它们。

回答"这些问题是不是单线程上没有的"：基本全是。P3/P4 是边界的发明物，单线程定义上不存在；P1/P2 是同一套语义在两个平台上的两张账单。这也解释了带病发布：开发与测试环境（DOM/jsdom、单 realm）里这些问题全部不可见 —— 与 #459 完全同一个模式。更准确地说这不是"Lynx 问题"而是 split topology 问题：universal-core 同时是 electron process-split（#472）的底座，同样的假阳性在 electron 的进程边界上会以 IPC 序列化的形式同样爆炸 —— 修 P1/P2 的受益面比 Lynx 大，这是给 upstream 的好论据。

归因分层：架构 · 成本模型 · 一行细节

层归因修复面
架构层universal-core 为 split 拓扑而生：把重放物化成 Blueprint/记录/命令是必要的（DOM 路径的"产物"就是 DOM 写本身，无需物化）。这一层没有错 —— 有边界就必须有物化不用修

新问题

这些框架差异，哪些是 Web 吵了十年的旧账，哪些是 Lynx 双线程新开的账？

最后一层抽象：把坐标系的轴分成两堆。这决定哪些结论可以从 Web 社区平移，哪些必须在 Lynx 上重新测 —— 也解释了为什么 Octane 这种高水平团队会踩到那个坑。

九根轴，两种出身

Web 旧账
render model：vdom diff vs 细粒度 effect vs owner 重放 —— js-framework-benchmark 吵到今天的同一题 Staging 的存在性：模板编译/静态提升 web 也有（cloneNode 就是 native 档）
Lynx 新账
判等语义 —— 单 realm 里 identity 免费又无害；跨线程后必须按值（Octane 案例＝标准标本） Naming —— 单 realm 里指针即身份，跨线程必须发明 id Delivery —— residual"何时过线"在 web 无意义 WireEncoding / Validation —— web 没有热路径消息边界 Driver / Handover —— 第一帧双渲染与认领（web 仅 SSR 有远亲）

九根轴里七根是双线程新开的账 —— "web 框架直接移植"注定踩坑的结构性原因： 它们的概念清单里没有这七根轴。Octane 的病灶恰好全落在新账区， 而它的编译语义创新（旧账区）平移无损。

v1 的八根轴 + 新增第九根（判等语义），且有了最好的标本：Octane 团队平台功课做得很深（__RenderPage 时机、优先级 token），仍然踩了新账区的坑 —— 因为那不是"知识"缺口，是"概念清单"缺口。这也是这份分类存在的意义：把新账列成清单，下一个框架照单自检。

VDOM vs Signal：Lynx 把两边的赌注都放大了

VDOM/重放家族在 Lynx 多赚的react / vdom / octane
batch 是天然形状
· 一次 commit = 一次 diff =
  一条消息 —— 批处理免费
· 极端形态 = Octane 背压合并：
  50 tick → 19 commit，
  updateStorm@30k 全场最快
· create/首帧：一遍式投影easy
  （render-to-* 生态现成）
Signal/effect 在 Lynx 多赚的vapor
不重渲染 = 不重发
· 点更新零 diff、零假阳性：
  select 39 字节；selectStorm@30k
  429ms vs vdom 5367ms (12.5×)
· web 上 signals 省 diff；
  Lynx 上还省 wire —— 双重红利
· 但代价前置：必须先建 Naming
  （effect 要能"指名"远端节点）

Web 的结论不能白拿：Lynx 给重放家族发了"批量免费"的新牌（Octane 的合并流水线是 极端好例），给 Signal 发了"wire 最小化"的新牌 —— 但 Signal 的牌必须先付 Naming 的门票（vapor 的整个 +b 工程），而重放家族必须先过判等这一关 （Octane 的 2.4MB 是没过关的代价）。

v1 的结论保留，但两边各加了一个 Octane 案例：批量红利的极端好例（背压合并）和重放家族的新前提（判等按值 —— web 上 vdom 不需要这一关，Lynx 上必须过）。诚实答案不变：交互重的 UI，signal 双重红利值回门票；静态重的 UI，重放+模板已贴地板。

IFR 是 SSR 的韵脚，不是它的复刻

Web SSR + hydrationLynx IFR + handover
第一帧生产者服务器（跨机器）主线程（跨 realm，同设备）
一遍式渲染器renderToString 生态成熟RL fork 之 / Octane 自建（冻结 hooks）/ Vue 待 D2
认领机制DOM 树遍历 + 就地绑定id 认领表（refMap / adoption / D1）
分歧代价hydration mismatch → 局部重渲染局部补（RL/D1）或确定性 repair（Octane）
独有难点序列化数据、流式事件重放（画得出但听不见的窗口）、id realm 对齐、每台设备每次冷启都在跑

RL 的 opcodes 干脆就是同一个渲染器的 SSR 输出档。但 Lynx 的新难点是真的： 第一帧和框架同机不同 realm，事件会在交接窗口里到达 —— RL 的 delayEvents + idSwap 和 Octane 的 FIFO replay 都是为此发明的。

给 Web 背景读者的桥（v1 恢复，Octane 列补全）：概念全对得上，但三个 Lynx 独有难点让"直接搬 SSR 方案"不够 —— 事件缓冲重放、双 realm id 对齐、以及成本模型（SSR 每次部署跑一次，IFR 每台设备每次冷启跑，一遍式渲染器的每毫秒乘以 DAU）。

最初的五问，现在的五答

1 · 模型与位置Octane = React 状态模型 + 编译期静态依赖（RC 一族，非 signal）+ owner 重放；plan 是 data/block/bundle 的 residual（≈ vapor +b!），但 wire 退化成 ops/node 全量 —— 矩阵里要占两行的框架
2 · 性能后果重放宽度 × 判等失败 × 单命令成本：select 慢 8×（报文 2.4MB vs vapor 39B、与变更量无关）；风暴反超 = 背压合并（50 tick→19 commit），不是渲染器快
3 · 好设计 / 弯路抄 Octane：背压合并、hooks 编译语义、优先级 token、__RenderPage 时机。抄 RL：判等深比较、一遍式 driver、树认领。抄 Vue：flat wire、BG 无感 IFR。弯路分了 A/B/C 三类，B 类（单 realm 直觉）是主病灶
4 · 共性 → 平台八件套三度重复发明（判等语义列第 0）；四条平台建议 + 五个 Octane 侧 mini-RFC —— 同一份证据，两个受益人
5 · 旧账 / 新账render model 是旧账可平移；九轴里七根新账 —— signal 有双重红利但付 Naming 门票，重放家族拿批量免费但必须先过判等关

五问五答回归，全部按 v2 的证据更新。只记一句：三个框架的分歧集中在平台没提供的地方；平台提供了的（list 回收），三家一致 —— 而 Octane 的教训把"该提供什么"的清单加长了一件：判等语义。

一页总结

它是什么React 状态模型 + 编译期静态依赖（RC 一族，非 signal）+ owner 重放；编译产物 = plan（data/block/bundle，≈ vapor +b!）+ 每 render 槽值数组（≡ Snapshot values）
慢在哪重放宽度（owner=App，无 memo）× 判等失败（非原始槽值按 identity）× 单命令成本（对象 clone + 双段校验）—— select 报文 2.4MB 而 vapor 39B，与变更量无关
两个修复#459 = 单 realm 直觉的功能版（B 类，已修+补 test rig）；#578 = 年轻的整根重放（C 类，被 wire 放大；owner 宽度与判等未动，报文仍 2.4MB）
真正的好东西背压合并流水线（50 tick→19 commit，风暴反超 2× 的真机制）、__RenderPage 时机、优先级 token、list 回收、一遍式 driver + adoption
怎么修R1 判等按值 → R5 自动 memo → R2 洞表上 wire → R3 验证降级 → R4 ack 惰性化；终点 = vapor +b! 格 + oneshot + 合并流水线，select 应回两位数 ms

一句话版：Octane 的编译器已经把 Lynx 需要的一切都算出来了 —— 它只是还没把这些信息接到跨线程的 wire 上；接上的那天，它就落在我们矩阵里已被验证过的那一格。
