# 统一基准矩阵

在同一台机器、同一阶梯上，把 IFR 风格、VDOM vs Vapor、React vs Vue
**一眼看完**——又不把不同量纲混在一起。

**怎么读 storms：Select = 点状更新**（每次只动选中态/少量 class）；
**Update = 批量更新**（每轮改很多行）。别把两条曲线当成同一种工作负载。

## 怎么读

1. **结论** — 好消化的产品选择；数字用来核对。
2. **Storm 表 / 图** — 点状（select）vs 批量（update）延迟。第三个框架家族
   [Octane](https://github.com/octanejs/octane) 在这张表里是完整的一列，
   也是它差距最悬殊的地方，见下。
3. **FCP 表 / 图** — content-probe 首帧阶梯（另一套仪器！）。
4. **优化 flag 矩阵** — V4 记法 `render [+b[:d|c|e]] [+ifr[:c|e]]` 下的
   全部合法组合（基线 = per-node；`+b` = block templates；`+b:e` =
   engine 档，web 上 N/A 且已省略；`+ifr:e` = 仅首帧引擎绘制），逐格测
   create/update，附单 flag marginal 因子归因与页内完整图例。形式化见
   [`GRAPH-ENG-REPORT.md`](https://github.com/Huxpro/vue-lynx/blob/vapor/packages/ifr-bench/GRAPH-ENG-REPORT.md) §1.3c。

## Octane（第三个框架家族）

[octanejs/octane](https://github.com/octanejs/octane) 自带一个私有的 Lynx
renderer（`@octanejs/lynx`）。它出现在 storm 表和 FCP 阶梯里，用的是**和其它
所有 cell 完全相同的两套仪器**——它没有自己专属的 workload。

这依赖一个上游修复。在
[octanejs/octane#459](https://github.com/octanejs/octane/pull/459) 之前，Octane
在 Lynx for Web 上收不到任何点击，背景线程也从不提交：web 上两个 Lynx 线程是
不同的 JS realm（背景在 iframe 里），而 Octane 的校验用的是 realm 本地的
`getPrototypeOf(v) === Object.prototype`，于是主线程拒收了背景发来的每一条消息。
**本站在该修复之前发布的 Octane 数字已被取代**，其中那一节 startup/mount-create
也已删除。

按「每次操作动了树的多大比例」排开，结论就很清楚：

| 操作 | 动了多少树 | octane vs `vdom` |
|---|---|---|
| `select` | 一行 | 13–19× |
| `update10th` | 每 10 行 | 10–12× |
| `create` / FCP | 整棵树 | 1.2–2.1× |
| `updateStorm` | 反复全量改 | 1.11× → **0.86×** |

差距取决于**操作次数**，不是节点数量。Octane 的协议是 per-node 对象命令 +
structured clone，改一行也要把那一行的节点命令当作新对象重发一遍；Vue 各格把
同样的改动压成扁平 ops 数组里的几个数字。而当整棵树本来就要重写时，这份每节点
成本不再是额外开销，Octane 的「直接」反而赢。

方法、注意事项与完整解读：
[`packages/benchmark/OCTANE.md`](https://github.com/Huxpro/vue-lynx/blob/vapor/packages/benchmark/OCTANE.md)。

## 环境规则

- **lynx-web** — 主产品量纲（本报告）。
- **bare-dom** / **node-jitless** — 不同仪器；禁止跨环境比毫秒。
